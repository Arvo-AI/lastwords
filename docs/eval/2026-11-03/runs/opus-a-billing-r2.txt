**What's happening**
- `billing-api` is being **OOMKilled** (exit code 137) because it hits its 256Mi memory limit. It has restarted 4 times in about 6 minutes and is now in CrashLoopBackOff.
- Memory climbs steadily at about **5 MiB/s** from startup until the kill, roughly 60–70s after the 20s warm-up. Every run looks the same: `rendered 0 → 500 → 1000 → 1500 invoices`, then it dies.
- That works out to about **100–130 KB kept per rendered invoice**. Memory grows with the number of invoices and is never released. That's a leak, not a limit that's set too low. Raising the limit would only delay the crash.
- `checkout` in the same namespace is OOM-looping the same way (384Mi limit, ~6 MiB/s), so it may share the same code.

**Likely fix**
In the invoice rendering loop, look for something that grows with every invoice and is never cleared:
- invoices or rendered output (`[]byte`, `bytes.Buffer`, strings) appended to a package-level slice or map, or to an unbounded "cache"
- a buffer that's reused but never `Reset()`, or `sync.Pool` objects kept after use
- goroutines started per invoice that never exit, holding on to their data

Fix: drop each rendered invoice once it's written or sent. If you need a cache, give it a size limit or an LRU. Stream output instead of collecting it.
