# Get core dumps from crashing Kubernetes pods

When a process in a pod segfaults, the kernel writes a core dump based on the node's `/proc/sys/kernel/core_pattern`, not the container's. On EKS's Amazon Linux 2023 nodes that is:

```
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h
```

So the core goes to the node's systemd journal, where `kubectl` cannot reach it, and nothing links it to a pod. To get cores you need something on every node that owns `core_pattern`, matches each core to its pod, and keeps cores from filling the disk.

IBM's core-dump-handler used to be the usual answer. Its repository (github.com/IBM/core-dump-handler) and docs site both returned 404 when we checked on 2026-11-03.

Verified 2026-11-03 on EKS 1.33 (Amazon Linux 2023, kernel 6.12, containerd 2.3).

## With lastwords

[lastwords](../../README.md) is a DaemonSet that, with `coreDumps.enabled=true`, points `core_pattern` at a small helper on the node. The helper gzips the core next to the process's memory map, finds the pod from the crashing process's cgroup, and stores it as a capture with the pod's logs.

```sh
helm install lastwords oci://ghcr.io/arvo-ai/charts/lastwords -n lastwords --create-namespace \
  --set coreDumps.enabled=true
```

On our nodes, `core_pattern` became:

```
|/var/lib/lastwords/bin/lastwords core-handler %P %s %t %e
```

A C worker that dereferences a NULL pointer on a corrupt upload ([source](../../examples/segfault/worker.c)) produced this capture:

```
# thumbnails-54bc987d4b-qdmjm/segfault dumped core: SIGSEGV in /usr/local/bin/thumbnail-worker

## Files
- `core.gz` (21 KiB): Gzipped core dump of /usr/local/bin/thumbnail-worker.
- `maps.txt` (2 KiB): Memory map of the process at crash time (for symbolizing addresses)
- `crash.txt` (360 B): Crash metadata from the kernel
```

## Read the core

You need the same binary the process ran. Copy it out of the same image, then:

```sh
kubectl lastwords get <capture-id> core.gz
gunzip core.gz
gdb -batch -ex bt ./thumbnail-worker core
```

What it printed for us:

```
Core was generated by `thumbnail-worker'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x000056446db9b265 in checksum (img=0x0) at /src/worker.c:19
#1  0x000056446db9b376 in main () at /src/worker.c:32
```

`img=0x0` is the bug: `decode()` returns NULL for a corrupt file and `main` passes it on without checking. We ran gdb in a `debian:12-slim` pod with the binary copied in by an init container from the same image. You don't need a node shell.

## What protects the node

A crash-looping pod can segfault every few seconds, and each core can be the size of the process's memory.
- **Per-pod budget:** at most 3 cores per pod in 30 minutes.
- **Queue limit:** at most 4 cores waiting to be picked up.
- **Disk floor:** cores are only written while free disk space is at least twice `coreDumps.maxBytes` (2 GiB by default) and at least 10% of the filesystem.
- **Agent down:** the helper enforces all of these limits itself, so they still apply when the agent is gone.

On `helm uninstall`, the agent writes the original `core_pattern` back. On our nodes it was `systemd-coredump` again afterwards. The helper binary stays in `/var/lib/lastwords/bin` on purpose: if the agent was killed before it could restore `core_pattern`, the kernel still finds a working program to pipe cores to.

## Caveats

- `core_pattern` is global to the node, so only one tool can own it. If you already ship cores somewhere (systemd-coredump to a log pipeline, for example), leave `coreDumps.enabled` off.
- On cgroup v2 with Kubernetes 1.28 or later, a child process killed by the OOM killer takes the whole container with it (`memory.oom.group`). That is an OOM kill, not a core dump, and lastwords records it as `oomkill`.
- Go programs don't dump core on a panic unless `GOTRACEBACK=crash` is set. lastwords takes the crash site from the panic in the logs instead.
